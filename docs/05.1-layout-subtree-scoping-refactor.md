## 拒否された設計の「本当の問題」はどこにあったか

`05-layout-subtree-scoping-refactor.md` が per-item independent effect 案を却下した理由を読み直すと、問題は「アイテムごとに状態を持つこと」自体ではなく、

> Solidの複数の独立した`createComputed`は同一トランザクション内でまとめてバッチ実行されるが、**兄弟間・親子間の実行順序は保証されない**

という一点に集約されます。つまり「各アイテムが自分の`createEffect`/`createComputed`を持ち、それぞれが独立にスケジューリングされる」設計だから壊れるのであって、**親のレイアウト計算が子のレイアウト計算を直接呼び出す**形にすれば、順序はJavaScriptの関数呼び出しそのものが保証してくれます。

Solidの`createMemo`は pull-based（遅延評価）です。あるmemoの中で別のmemoを読む（呼ぶ）と、そのmemoが stale なら**その場で同期的に再計算されてから値が返る**——これはSolidの実装詳細ではなく、memoの定義そのものです。実際`resolvedColor`は既にこれをやっています（子が`parent.resolvedColor`を読むと、親のmemoが必要なら再計算されてから値が返る）。これは継承（親→子）方向ですが、**同じ仕組みは集約（子→親）方向にもそのまま使えます**。

## 設計: 「independent effect」ではなく「再帰的memoチェーン」

各`Item`に、`layoutSubtree`の3フェーズ全部を1つにまとめた自分専用のmemoを持たせます。

```js
// item.js のコンストラクタ内、他のmemoと同じ createRoot ブロックの中
this._layoutResult = createMemo(() => this._computeLayout());
```

```js
_computeLayout() {
  // Phase 1相当: 自分のDOMだけを触る副作用。他アイテムに依存しないので
  // 実行順序は無関係(子より先でも後でもよい)。
  this.updateText();
  this.updateStatus();
  this.updateValue();
  this.updateIcon();
  this.updateNotes();

  // Phase 2相当: 自分のcontent boxを計測して即書き込む。
  const { content } = this.dom;
  const size = [
    Math.max(content.offsetWidth, content.scrollWidth),
    Math.max(content.offsetHeight, content.scrollHeight),
  ];
  const fo = content.parentNode;
  fo.setAttribute("width", String(size[0]));
  fo.setAttribute("height", String(size[1]));

  // Phase 3相当・肝心の部分: 子のmemoを「呼ぶ」。
  // stale な子はここで同期的に再計算されてから戻ってくる。
  // これが post-order を保証する唯一の理由 —
  // Solidのエフェクトスケジューラの順序保証には一切頼っていない。
  if (!this.collapsed) {
    this._childrenVersion(); // track insertion/removal
    this.children.forEach((child) => child._layoutResult());
  }

  const { resolvedLayout, resolvedShape, dom } = this;
  dom.text.style.color = this.resolvedTextColor;
  dom.node.dataset.shape = resolvedShape.id;
  dom.node.dataset.align = resolvedLayout.computeAlignment(this);
  dom.connectors.innerHTML = "";
  resolvedLayout.update(this);   // 子のsize/positionは既に確定済み
  resolvedShape.update(this);

  return this.size; // getBBox()
}
```

Mapは薄い1つのルートだけを持ちます。

```js
createComputed(() => {
  this._root._layoutResult(); // pull chain の起点。ここから先は全部memo。
  this.node.setAttribute("width", String(this._root.size[0]));
  this.node.setAttribute("height", String(this._root.size[1]));
  bumpDirty();
});
```

これで`map.js`の`layoutSubtree`/`updateContent`/`measureAndSizeContent`/`writeLayout`という4つの外部関数は不要になり、責務が`Item`自身に移るだけで、コードの複雑さの総量はほぼ変わりません（dirtyフラグや`markDirty`/`markSubtreeDirty`のような**新しい状態管理を一切増やさずに済む**のが利点です）。

## なぜ「動かした部分だけ」再計算されるのか

`_childrenVersion`のbumpは、そのitemの`_layoutResult`だけを invalidate します。親の`_layoutResult`はその子の`_layoutResult()`を呼んでいるので、子が invalidate されれば親も再計算対象になり、これが根まで連鎖します。しかし**兄弟枝は誰にも読まれていないので、Solidのメモ化により完全にスキップされます**。これがまさに求めていた「ノードを動かしたら、その経路だけ再計算される」という挙動そのものです。手動の`dirty`フラグを持ち出さなくても、memoの依存追跡が dirty 管理そのものです。

## 副産物: 継承プロパティの`markSubtreeDirty`が丸ごと不要になる

dirty-flag案では「`color`/`textColor`/`shape`/`layout`だけは特別に子孫全部を`markSubtreeDirty`する」という非対称な特別扱いが必要でした（05のドキュメントの「既知の制約」節）。

memoチェーン案ではこれが**発生しません**。`resolvedColor`等は既に「子が親を読む」下方向のpull-based memoなので、祖先の色が変わったとき、**実際にそのmemoを読んでいる子孫だけ**が自動的に再計算されます。上方向（layout集約）と下方向（inheritance）が別々の独立したmemoチェーンとして共存でき、互いに特別扱いを必要としません。dirty-flag案が抱えていた「上方向はancestorだけ辿ればいいが、この4つだけ下方向も辿る必要がある」という非対称性そのものが設計上消えます。

## 非signal由来の特殊トリガーの扱い

`05`のPhase 4で挙がっていた3つのケースは、memo設計だとむしろ**現状よりスコープを狭くできます**。

1. **`item.side`変更**（`SetSide`）: 現状は`item.map?.requestLayout()`で全体再計算。memo設計では、そのitem専用の小さなバージョンsignalを追加し、`_computeLayout`の中でそれを読むだけにします。
   ```js
   const [sideVersion, bumpSideVersion] = createSignal(0);
   this._sideVersion = sideVersion;
   this._bumpSideVersion = () => bumpSideVersion(v => v + 1);
   // _computeLayout の先頭で this._sideVersion() を読む
   ```
   `SetSide.do()/undo()`は`item._bumpSideVersion()`を呼ぶだけ。影響範囲はそのitemと祖先のみ（兄弟は無関係）——現状の`map.requestLayout()`より狭く、正確です。

2. **contentEditableのライブ入力**（`item.js`の`"input"`ハンドラ）: 同様に、そのitem専用のバージョンをbumpするだけで十分です。現状の`this.map.requestLayout()`（全体）より狭いスコープになります。

3. **フォントサイズズーム**（`adjustFontSize`）: これだけは意図的に全体トリガーとして残します。Map単位で共有する`fontSizeVersion`シグナルを用意し、**全アイテムの**`_computeLayout`がこれを読むようにします。ズームは全ノードの実測サイズに影響する唯一の正当な全体トリガーなので、`05`のPhase 4と同じ結論のまま、実装だけがシンプルになります。

## 留意点として明示しておきたいこと

- `createMemo`の中でDOM書き込み（副作用）をしているのは、Solidの推奨作法から外れます。ただしこの副作用は「このmemoの外から読まれるのは親の`_layoutResult()`呼び出しか、Mapのルート`createComputed`だけ」という前提の上に成り立っているので、**UIコンポーネント側がうっかり`item._layoutResult()`を読んでしまう**と、意図しないタイミングでDOM書き込みが走るリスクがあります。命名を`_`prefixのまま外部非公開に保つか、専用のシンボルで隠すなど、誤用防止は要検討です。
- `getBBox()`/`offsetWidth`自体のreflowコストは消えません。memo化で減らせるのは「無関係な枝の再計測をスキップできる」点だけです。
- `position`（transform属性）は親の`_computeLayout`内で子に書き込まれる副作用のままです。子自身の`_layoutResult`の戻り値ではないので、「子のposition変化に子自身が反応する」経路は元々存在しません（現状のコードでも同様の構造なので、これは新たに持ち込む制約ではありません）。

この設計なら、`05`が却下した「アイテムごとの独立effect」の**弱点だけをピンポイントで解消**しつつ、`CLAUDE.md`の「後方互換性は不要」「関数は小さく焦点を絞る」という方針とも矛盾しません（4つの外部関数がItemのメソッド1つに集約されるだけで、状態の種類は増えません）。
