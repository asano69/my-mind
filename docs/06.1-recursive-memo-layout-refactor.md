# 再帰的memoチェーンによる大量ノード向けレイアウト改善計画

## 背景

大量ノードを持つマインドマップでは、1つのノードを編集しただけでも`map.js`のルート`createComputed`がツリー全体のsignalを読み直し、全ノードのDOM更新・計測・レイアウト書き込みを再実行してしまう。`docs/05-layout-subtree-scoping-refactor.md`ではdirtyフラグ方式を検討したが、`docs/05.1-layout-subtree-scoping-refactor.md`で整理された通り、より自然な解決策は「アイテムごとの独立effect」ではなく、親が子のmemoを同期的に読む**再帰的memoチェーン**である。

この計画では、Solidのpull-basedな`createMemo`を使い、変更されたノードからルートまでの依存経路だけを再計算対象にする。手動dirtyフラグや継承プロパティ専用の`markSubtreeDirty()`は追加しない。

## 目的

- 葉ノードのテキスト編集、status/value/icon/notes変更、collapse切り替えなどで、無関係な兄弟サブツリーの再計測を避ける。
- 既存のpost-orderレイアウト順序を、SolidのeffectスケジューラではなくJavaScriptの関数呼び出し順で保証する。
- レイアウト責務を`Item`自身へ寄せ、`map.js`の全体再帰関数を段階的に薄くする。
- 実装中も各フェーズを小さく保ち、計測結果で効果を確認しながら進める。

## Non-goals

- `layout/*.js`の幾何計算アルゴリズムそのものは変更しない。
- 複数の独立した`createEffect`/`createComputed`をアイテムごとに作る案は完全には否定しない。ただし、MVPでは「順序制御をSolidのスケジューラへ暗黙に任せる」形では採用せず、Phase 0.5のスパイクで成立条件を検証する。
- `getBBox()`、`offsetWidth`、`scrollWidth`などDOM計測自体のコストを消すことは目的にしない。今回減らすのは「無関係な枝まで計測する回数」である。
- フォントサイズ変更のように全ノードの実測サイズへ影響する操作まで部分更新化しない。

## 独立effect案についての判断

Solid.jsらしさだけを見ると、「各Itemが自分のDOM同期effectを持つ」案は自然である。実際、text/status/value/icon/notesのように**そのItem自身のDOMだけを更新する処理**は独立effectと相性がよい。問題は、現在のレイアウトが単なるローカルDOM同期ではなく、次の順序依存を同じパスに含んでいる点にある。

- content DOMを書き換える。
- 各Itemの`foreignObject`サイズをDOMから測り、即座にwidth/heightへ書き戻す。
- 親レイアウトが子の`getBBox()`結果を読んで、子のpositionと親のconnectorを更新する。

したがって「Itemごとに独立したeffectを置くだけ」の設計は厳しい。親effectが子effectより先に走ると、親は古い子サイズを読む可能性がある。ただし、これは独立effectが絶対に不可能という意味ではない。成立させるには、少なくとも次のどちらかの明示的な順序制御が必要になる。

1. **分業型effect + 共有スケジューラ**: 各Itemのeffectは「自分がdirtyになった」ことだけを登録し、実際のDOM計測・レイアウト書き込みはMap単位のスケジューラがpost-orderでflushする。これはSolidのeffectを通知機構として使う案で、実質的にはdirtyキュー方式に近い。
2. **子から親への明示的な依存値**: 子effect/memoが「確定済みサイズ」をsignalとして公開し、親effectがその値を読む。これなら親は子サイズに依存できるが、DOM書き込み、`getBBox()`、connector更新、position更新の境界をかなり細かく分ける必要がある。

今回の第一候補を再帰的memoチェーンにする理由は、独立effect案が「かなり無理」だからではなく、**現在のpost-order不変条件を最小の設計変更で保てるから**である。親が子の`_layoutResult()`を直接読むなら、順序はSolidの非公開スケジューリングではなくJavaScriptの呼び出し順で決まる。一方で、独立effect案はSolidらしい可能性があるため、実装前に小さなスパイクで検証する価値はある。

## 採用設計

各`Item`が自分のサブツリーのレイアウト結果を返す非公開memoを持つ。

```js
this._layoutResult = createMemo(() => this._computeLayout());
```

`_computeLayout()`は、現在`map.js`側にある`updateContent`、`measureAndSizeContent`、`writeLayout`相当の処理を1アイテム単位で実行する。子のサイズが必要な箇所では、親が子の`_layoutResult()`を直接呼ぶ。子memoがstaleならその場で同期的に再計算されてから値が返るため、親は常に確定済みの子サイズを読める。

Map側はルートだけを読む。

```js
createComputed(() => {
  const rootSize = this._root._layoutResult();
  this.node.setAttribute("width", String(rootSize[0]));
  this.node.setAttribute("height", String(rootSize[1]));
  bumpDirty();
});
```

これにより、通常のノード更新では「更新されたノード自身のmemo」と「それを読む祖先memo」だけが再計算される。兄弟ブランチは依存経路に含まれないため、Solidのメモ化でスキップされる。

## 再帰的memoチェーンからper-item effectへ段階移行できるか

現実的である。ただし、最初からレイアウト全体を独立effectへ分割するのではなく、**順序依存のない責務からeffect化する**のが安全な移行順になる。再帰的memoチェーンを先に入れる価値は、親子のpost-order不変条件を1箇所に保ったまま、どの処理が本当に順序依存しているかを切り分けられる点にある。

移行の目安は次の通り。

1. **ローカルDOM同期をeffect化する**: `updateText()`、`updateIcon()`、`updateNotes()`のように自分のDOMだけを書き換え、子サイズや親レイアウトを読まない処理からper-item effectへ戻す。この段階では、サイズが変わりうる更新の後に対象itemのレイアウトmemoをinvalidateするための小さなversion signalだけを残す。
2. **サイズ計測を独立したmemo/effectへ分離する**: content更新後の`foreignObject` width/height確定を、item単位の「contentSize確定ステップ」として切り出す。ただし親レイアウトは、子のサイズ確定後にだけ動く必要があるため、ここで子サイズsignalまたは共有flush境界が必要になる。
3. **親レイアウト書き込みを最後に分離する**: `resolvedLayout.update(item)`は子の確定済みサイズとposition書き込みに依存するため、最も後回しにする。ここまで来ると、独立effect案は「各effectが好きに走る」形ではなく、「Solidの依存グラフ + 明示的なサイズ確定値」で順序を表現する形になる。

つまり、再帰的memoチェーンは行き止まりではなく、後からSolidらしいeffect構成へ寄せるための**足場**として使える。ただし移行中も、以下の境界は守る。

- effect化してよいのは、入力signalから自分のDOMだけへ閉じる処理を優先する。
- DOM計測値を親が読む処理は、必ず「子の計測が終わった」という依存値を経由する。
- `resolvedLayout.update(item)`とconnector描画は、最後までpost-order保証を失わない。
- effect化で測定回数が増えるなら採用しない。大量ノード対策の主目的は、Solidらしい分割そのものではなく、無関係な枝の計測を減らすことである。

このため、本計画のPhase 6後に、別フェーズとして「effect化の漸進移行」を追加するのが現実的である。

## フェーズ計画

### Phase 0 — 計測基盤と現状特性化

本番挙動を変えず、現在の全体再計算コストを数値化する。

- `layoutSubtree`、`updateContent`、`measureAndSizeContent`、`writeLayout`の訪問数を開発時だけ記録できる小さな計測フックを追加する。
- 以下のシナリオで、1レイアウトパスあたりの訪問ノード数と実行時間を記録する。
  - 50〜100ノード程度の深い木で、葉ノードのテキストを編集する。
  - 同じ木で、葉ノードのstatus/value/icon/notesを変更する。
  - 中間ノードのcollapsedを切り替える。
  - ルートのlayout/shape/color/textColorを変更する。
  - フォントサイズズームを実行する。
- Phase 0の計測値を、このリファクタリングの採否判断の基準にする。Phase 3以降で改善が確認できなければ中断または差し戻しを検討する。
- 計測フックは本番コードに恒久的に残さない。残す場合はテスト専用、または明示的な開発フラグ配下に限定する。

リスク: 低。挙動変更を伴わないが、計測コードを本番パスへ残さないよう注意する。

### Phase 0.5 — 独立effect案の成立条件スパイク

再帰的memoチェーンへ進む前に、独立effect案が本当に不利かを小さく検証する。ここでは本番実装へ進まず、破棄可能なブランチまたはテスト用コードで確認する。

- 3階層以上の小さなツリーを使い、子のcontent更新、子のforeignObjectサイズ確定、親の`resolvedLayout.update()`が常に期待順になるかを観察する。
- itemごとのeffectだけで順序が安定するか、`batch()`中の複数更新、insert/remove、collapse解除直後、contentEditable入力中でも確認する。
- 順序が不安定な場合、共有スケジューラ方式または子サイズsignal方式を追加した時点の複雑さを、再帰的memoチェーン案と比較する。
- 独立effect案が十分単純に成立するなら、Phase 1以降を見直し、DOM同期だけをper-item effectへ戻す選択肢を残す。

リスク: 低。目的は設計判断であり、本番コードへ未検証の順序依存を入れない。

### Phase 1 — `Item`単位の小さなレイアウトメソッドを切り出す

memo化の前に、既存処理を移動しやすい形へ分割する。

- `map.js`の`updateContent(item)`相当を、`Item`の`_updateLayoutContent()`へ移す。
- `measureAndSizeContent(item)`相当を、`Item`の`_measureOwnContent()`へ移す。
- `writeLayout(item)`相当のうち、1アイテムの見た目更新とレイアウト委譲を`Item`の`_writeOwnLayout()`へ寄せる。
- この段階では、既存の`layoutSubtree`から新しいメソッドを呼ぶだけにし、再計算範囲はまだ全ツリーのままにする。
- 既存テストに加え、メソッド切り出し後もノードのテキスト、アイコン、status/value、notes、shape、connectorが従来通り更新されることを確認する。

リスク: 中。処理移動による回帰が主なリスクなので、memo化より前に純粋なリファクタリングとして分ける。

### Phase 2 — `Item._layoutResult` memoを導入するが、Map側の全体再帰は残す

新しい依存グラフを作り始めるが、切り替えはまだ行わない。

- `Item`の既存`createRoot`ブロック内に`this._layoutResult = createMemo(() => this._computeLayout())`を追加する。
- `_computeLayout()`ではPhase 1で切り出した3つの小メソッドを順に呼ぶ。
- collapsedでない場合だけ、`this._childrenVersion()`を読んだ上で子の`_layoutResult()`を呼ぶ。
- `_computeLayout()`は最後に`this.size`を返す。
- この時点ではMapの`createComputed`は従来の`layoutSubtree(this._root)`を使い続ける。新memoはテストから明示的に呼び、依存関係と戻り値の正しさを確認する。
- テストでは、子のtext変更時に子memoと祖先memoが再評価され、無関係な兄弟memoは再評価されないことを計測用スパイで確認する。

リスク: 中。memo内部でDOM書き込みを行うため、外部公開しない命名と配置を徹底する。

### Phase 3 — Mapのレイアウト起点をルートmemoへ切り替える

実際に全体再帰を廃止し、再帰的memoチェーンを正式なレイアウト経路にする。

- `map.js`のルート`createComputed`を、`layoutSubtree(this._root)`ではなく`this._root._layoutResult()`を読む形に変更する。
- ルートmemoの戻り値を使ってSVGの`width`/`height`を更新する。
- 旧`layoutSubtree`、`updateContent`、`measureAndSizeContent`、`writeLayout`はMap側から参照されなくなった時点で削除する。
- 既存の`requestLayout()`は、非signal由来の再計算トリガー用に一旦残す。
- Phase 0と同じシナリオを再計測し、葉ノード編集や局所的なstatus/value変更で訪問数がツリー全体ではなく変更経路中心に縮小していることを確認する。

リスク: 高。このフェーズが挙動切り替え点なので、手動確認と回帰テストを厚くする。

### Phase 4 — 非signal由来トリガーを局所化する

`docs/05.1-layout-subtree-scoping-refactor.md`で挙げられた3つの特殊ケースを、全体再計算から必要範囲の再計算へ縮小する。

- `item.side`変更用に、各`Item`へ`_sideVersion`と`_bumpSideVersion()`を追加する。`_computeLayout()`で`_sideVersion()`を読む。
- `SetSide.do()`/`undo()`や`mergeWith`など、sideを書き換える箇所では対象itemの`_bumpSideVersion()`を呼ぶ。
- contentEditableのライブ`input`では、対象item専用の`_contentVersion`または既存signal更新へ寄せ、対象itemと祖先だけを再計算させる。
- フォントサイズズームは全ノードの実測サイズに影響するため、Map単位の`fontSizeVersion`を用意し、全itemの`_computeLayout()`で読む。`adjustFontSize()`ではこのversionをbumpする。
- `requestLayout()`の用途を棚卸しし、局所versionで置き換えられる呼び出しと、全体versionが必要な呼び出しを分離する。

リスク: 中。呼び忘れがあると特定操作だけ更新漏れになるため、各トリガーごとに回帰テストを追加する。

### Phase 5 — 継承memoとの相互作用を確認する

下方向の継承memoと上方向のレイアウトmemoが干渉しないことを確認する。

- `resolvedColor`、`resolvedTextColor`、`resolvedShape`、`resolvedLayout`を読む箇所が`_computeLayout()`内に収まっていることを確認する。
- ルートのcolor/textColor/shape/layout変更で、明示上書きしていない子孫だけが正しく再描画されることをテストする。
- 子孫側で明示上書きしている場合、祖先変更の影響を受けないことをテストする。
- dirtyフラグ方式で必要だった`markSubtreeDirty()`相当の特別扱いを追加していないことを確認する。

リスク: 中。見た目の継承はユーザーに分かりやすい不具合として出るため、UI確認も行う。

### Phase 6 — 後片付けと公開境界の整理

内部APIが漏れないようにし、長期保守しやすい形へ整える。

- `_layoutResult`、`_computeLayout()`、各version bump関数がUIコンポーネントや外部モジュールから直接使われていないことを確認する。
- 必要なら`Symbol`または専用モジュール内の非export関数で、レイアウト内部APIを隠す。
- Phase 0の一時計測コードを削除する。
- 大量ノードの手動確認手順と期待値をドキュメントに残す。
- `docs/05-layout-subtree-scoping-refactor.md`のdirtyフラグ案は歴史的検討として残し、このドキュメントを実装方針として参照する。

リスク: 低。主に整理フェーズであり、挙動変更は避ける。

### Phase 7 — ローカルDOM同期のper-item effect化

再帰的memoチェーンで大量ノード時の再計算範囲を縮小できた後、順序依存の少ない処理からSolidのeffectへ戻す。

- `updateText()`、`updateIcon()`、`updateNotes()`など、自分のDOMだけを更新する処理をItemごとのeffectへ移す。
- status/valueは子孫集約memoに依存する場合があるため、先に影響範囲を計測し、必要なら後回しにする。
- text変更などcontent boxサイズへ影響する処理では、DOM同期後に対象itemのlayout invalidation用versionをbumpする。
- このフェーズでは`resolvedLayout.update(item)`やconnector描画はまだ再帰的memoチェーン側に残す。

リスク: 中。DOM同期とlayout invalidationの順序を誤ると、入力中の表示やサイズ追従が壊れる。

### Phase 7 progress note

`updateText()`/`updateIcon()`/`updateNotes()` are now per-item
`createEffect`s created in `Item`'s constructor, alongside the existing
memo `createRoot` block. `updateStatus()`/`updateValue()` deliberately
stayed inside `computeLayout()`'s `_updateLayoutContent()` call, exactly
per this phase's plan, since `resolvedStatus`/`resolvedValue` read
child-aggregated memos and must stay part of the post-order pass.

Content-version bumping ended up asymmetric, and intentionally so:
`updateText()`/`updateIcon()` both call `_bumpContentVersion()` after an
actual DOM write, since both can change the content box's measured size
(text length, icon presence as a flex sibling). `updateNotes()` does
*not* bump -- the notes badge is absolutely positioned (see map.css's
`.content .notes` rule) and never affects the measured content box, so
bumping there would have reintroduced exactly the unnecessary
recomputation this phase set out to remove. Previously, all three ran
inside `computeLayout()` itself, so Solid's memo tracking picked up
`_icon()`/`_notes()` reads automatically; moving them out means the
layout memo no longer implicitly depends on those signals at all, so the
explicit bump (or lack of one) is now the only thing connecting a
content change to a layout recompute.

Manual "did this actually change" caching (an initial idea) turned out
unnecessary: `createSignal`/`createMemo` already skip notifying
subscribers when the new value equals the old one, so each effect only
re-runs when its own tracked signal's value genuinely changes.

One incidental fix: `findLinks()` (called from `updateText()`) now
guards against a missing `childNodes` property, since this method can
run automatically as soon as an item's `text` signal is set -- including
from lightweight DOM stand-ins in tests that don't implement
`childNodes` -- rather than only inside `computeLayout()`'s previously
fully-controlled call path.

### Post-Phase-7 bug: node dropped into a still-collapsed node loses
### its rendered content once expanded

Unrelated to the per-item effects above, but surfaced around the same
time: dragging a node into an already-collapsed target, then expanding
that target, could leave the moved node's content box stuck at a
zero-measured size (text effectively invisible). Root cause: `map.js`'s
Map-level computed only pulls a collapsed item's children once that
item's own `collapsed` signal flips back to false -- by which point
`insertChild()`'s own single-RAF remeasure fix (aimed at the standard
"foreignObject not yet painted" quirk) had already fired while still
hidden, so it never got consumed. The very first *real* remeasure then
happens synchronously, inside the same call that just removed the
`.collapsed` CSS class -- and that specific transition (display:none ->
visible, inside an SVG foreignObject) turns out to suffer the same
stale/zero-size synchronous-read quirk as the "freshly inserted, not
yet painted" case already documented elsewhere in this file and in
map.js's `show()`. Fixed by giving the `collapsed` setter its own
double-rAF-delayed remeasure pass over the newly revealed subtree (see
`_bumpSubtreeContentVersion()`), mirroring `show()`'s existing pattern
rather than inventing a new one.

### Phase 8 — 見送り（サイズ確定値を明示依存へ切り出す案）

当初の想定: 各ItemがcontentSize確定値をsignal/memoとして公開し、親レイアウトが
DOMから直接子の`getBBox()`を読む箇所を減らす。

**見送り理由（2026-08確認）**: このフェーズの主な動機は「全ツリー再計算コスト
の削減」だったが、その最大の発生源として想定していたフォントサイズズーム
（Phase 4で触れていた`adjustFontSize`/全ノードdirty化ケース）は、現在の
`map.js`の`adjustZoom()`実装には存在しない。ズームはSVGノード全体への
CSS `transform: scale()`のみで行われ、`font-size`はconstructorで一度設定
された後は変化しない（＝どのitemの実測サイズにも影響しない）。ブラウザ標準
のズームと同じ挙動である。

全ツリー再計算のトリガーが実質なくなった以上、残る更新経路（葉ノード編集・
collapse・value/status変更・color/layout継承）はすでにPhase 2〜7の再帰的
memoチェーンで変更経路のみに限定されており、Phase 8で見込める追加効果は
小さいと判断する。CLAUDE.mdの「複雑さに見合う効果がなければ実装しない」
方針に従い、実装しない。将来、実際に大量ノードで`getBBox()`呼び出し回数が
ボトルネックになると計測で確認できた場合にのみ再検討する。

リスク: 該当なし（未実施のため）。

## 実装時チェックリスト

- 葉ノード編集で、無関係な兄弟サブツリーのDOM計測が走らない。
- 子の追加・削除で、親の`_childrenVersion()`経由の依存が正しく更新される。
- collapsedなノードの子孫memoが不要に読まれない。
- side変更で左右レイアウトが更新される。
- contentEditable入力中にノードサイズと祖先レイアウトが追従する。
- フォントサイズズームでは全ノードが再計測される。
- color/textColor/shape/layoutの継承が従来通り反映される。
- undo/redo、ドラッグ&ドロップ、merge操作で更新漏れがない。
- memo内部のDOM書き込みを外部コードから偶発的に起動しない。
- effect化したローカルDOM同期が、layout invalidationより前に確実に完了している。
- effect化後も、親レイアウトが古い子サイズを読まない。

## 中断条件

- Phase 3後の計測で、葉ノード編集や局所更新の訪問数がPhase 0比で明確に減らない。
- memo内部副作用により、更新順序やテスト安定性がdirtyフラグ方式より悪化する。
- `_layoutResult()`の外部利用を防げず、保守上のリスクが高いと判断される。

これらに該当する場合は、Phase 3を差し戻し、`docs/05-layout-subtree-scoping-refactor.md`のdirtyフラグ方式へ戻るか、計測で特定された別のボトルネックを優先する。
